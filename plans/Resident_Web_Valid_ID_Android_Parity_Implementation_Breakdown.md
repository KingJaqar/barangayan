## 3. Target resident experience

Settings → Valid ID → Select ID type → Provide front photo → Confirm details → Review and submit → Pending verification.

| Step | Resident action | Completion requirement |
| --- | --- | --- |
| 1 — Select ID type | Choose from the shared ID list. Selecting Other reveals an exact ID-name field. | A selected type; a nonblank name for Other. Preserve the shared `Other: ` encoding. |
| 2 — Provide an ID photo | Upload a file or take a photo; inspect its preview. The back is not requested. | A successfully uploaded, readable JPG, PNG, or WebP front image, at most 5 MB (5,242,880 bytes). Continue opens editable details; it does not automatically invoke OCR. |
| 3 — Review and confirm details | Enter full name, ID number, birthday, and address, or choose Read details from photo to suggest them through OCR.space. Review/correct every value. Select birthday using month/day/year wheels. | Full name is required. Optional fields may remain blank when not printed on the front. Any supplied birthday must be a real, nonfuture date. OCR is optional and cannot gate Continue. |
| 4 — Review and submit | Read the front photo, ID type, and confirmed details. Use Previous to correct them, or Submit. | Successful publication of the exact reviewed photo and details. |

After submission, show confirmation and a Back to Settings action. Refresh verification status. Pending submission is not approval. A replacement for a verified ID requires a new staff review, matching Android. Confirmed ID details stay with the evidence and do not overwrite Profile fields.

### Data contract

- Keep one details draft with `{ fullName, idNumber, birthDate, address }`, initialized to empty strings. Manual edits and accepted OCR suggestions update this same draft. Track which fields the resident has edited (including explicitly cleared fields); OCR may fill only empty, untouched fields. Never prefill from Profile or require an extraction response/token for publication.
- Treat entered text as untrusted input. Display it through normal text/input rendering, never injected HTML. Do not invent or prefill ID evidence from Profile.
- Final publication uses `publishIdEvidence` with `submissionId`, `idType`, `frontPath`, and `confirmedDetails`, omitting `backPath`. Include all four detail keys, using empty strings for optional blanks. Review and submit the same parsed/trimmed values.
- Keep the staging image path separate from the helper's final version path when reconciling a saved row. Local object URLs are previews, never persistence identifiers.
- Reuse private Storage, RLS, tenant checks, immutable writes, and server-derived identity/decisions. Do not expose privileged keys, directly write verification status, or weaken access rules to make a request succeed.

### OCR.space contract, limits and setup

These are planned changes, not existing/deployed APIs. Preserve `extract-resident-id` and its mobile consumers. Add the isolated web function **`extract-resident-id-ocrspace`** in Phase 4, following the existing verified-user, resident-role, owner-path, caller-scoped Storage, CORS and server-only rate-limiter patterns. Keep gateway JWT verification and handler authorization. Reuse safe existing logic rather than duplicating authentication, but do not silently change shared/mobile extraction behavior.

- Browser request to the new function: authenticated JSON `{ frontPath, idType }`; response: `{ details: { fullName, idNumber, birthDate, address } }`, all strings. Here `frontPath` refers to an OCR derivative, never the original evidence path used for publication. Check the response shape before merging suggestions, then validate the confirmed draft with the shared schema. Missing fields remain blank; OCR never proves identity or approval.
- Preserve the original accepted photo and its 5,242,880-byte evidence limit. On an explicit read action, prepare a separate JPEG/PNG derivative using native browser image/canvas APIs, converting WebP as needed. Choose a conservative maximum of **900,000 bytes** for the derivative, below the documented free-tier 1 MB input cap. Bound conversion to at most three encode/resize attempts and the total OCR deadline; stop with manual-entry feedback if it cannot produce a decodable, nonempty image within the cap. Check dimensions and resource use before allocating a canvas; test large-dimension images and browser encoding failure. Do not silently reduce the quality of published evidence to satisfy OCR limits.
- Upload that derivative privately under a separate caller-owned version UUID/front filename, following the existing path contract. Keep its path distinct from both staging evidence and final publication. Reuse it for an explicit retry of the same photo where safe. The endpoint must independently check caller ownership, MIME/content agreement, supported JPEG/PNG bytes and the 900,000-byte cap before sending anything externally. Reject arbitrary URLs, signed URLs, foreign/legacy paths and unsupported input; never make the evidence bucket public. Use existing authorized draft-resource cleanup where available; no blanket deletion, background cleanup job or published-evidence deletion is introduced.
- From the function only, POST a multipart `file` to the fixed HTTPS endpoint `https://api.ocr.space/parse/image`, with the key in the `apikey` header. Use `OCREngine=2` and `language=auto`; request neither overlays nor searchable PDFs. Use native fetch/FormData; no new runtime dependency is planned. No direct browser-to-provider request, client-visible key, Google fallback, or paid endpoint.
- Treat provider JSON as untrusted. Check HTTP status, `IsErroredOnProcessing`, `OCRExitCode`, per-image `FileParseExitCode`, and nonempty `ParsedResults[].ParsedText`; HTTP 200 alone is insufficient. Bound response processing and map malformed, partial, empty, authentication, quota and provider failures to safe action-specific feedback. Never expose raw provider payloads, log ID text, or store raw recognized text.
- Inspect/reuse the existing `id-text.ts` parsing rules where compatible. Its current `parseIdText` silently slices fields at 200/200/1,000 characters. Do not carry silent truncation into the web integration: leave an over-limit suggestion blank with a readable field warning and allow manual correction. Use a backward-compatible parser extension with existing-client tests if needed; do not change old callers implicitly. Uncertain/malformed/future birthday suggestions remain blank with correction feedback; never invent a date or name.
- Current documented free-tier limits are **25,000 requests/month and 500/day/IP**, without an uptime guarantee. Server egress may share an IP, so the daily cap is not per resident. Reuse the existing server-only five-per-minute resident limiter; it is not a global quota counter. No automatic retries or key rotation to evade caps. Provider quota errors leave manual entry usable; no paid upgrade or new quota-storage system is in scope. Recheck limits before implementation/release. [API and limits](https://ocr.space/ocrapi), [free-service FAQ](https://ocr.space/faq).
- Clearly disclose third-party processing before the read action. OCR.space states uploaded documents are deleted after processing; this is a provider policy, not an independently verified guarantee. Do not request a searchable PDF or claim compliance/accuracy certification. Manual entry avoids sending the photo to this provider. [Privacy policy](https://ocr.space/privacypolicy).

## 6. Bounded execution and error handling

These rules apply to implementation and release verification; they do not authorize new UI flows or a general transport refactor.

### Draft transitions

| Event | Required state behavior |
| --- | --- |
| Previous/re-enter step | Preserve the accepted photo and details. Cancel/invalidate a departing step's OCR action. Do not re-upload, re-read or publish automatically. |
| Successful new photo | Advance the photo revision; invalidate old replies/derivative; reset details and edit markers, and clear review confirmation. Failed/cancelled candidates preserve the accepted photo/details. |
| Type/details edited | Preserve corrected fields, invalidate the prior review snapshot, and require review again. A pending/unknown publication keeps its original snapshot frozen. |
| Manual detail entry | Edit the canonical draft locally. Typing, birthday changes and field validation do not start reads, uploads or provider requests. |
| Explicit OCR read/retry | Acquire one action ticket for the current account/photo/type. Fill only empty untouched fields on a valid current response; preserve edits and invalidate review. No recursive or automatic retry. |
| OCR cancel/timeout/failure | Abort supported transport, invalidate the ticket and release its loading state; preserve photo/details and allow manual completion. Stale results cannot mutate or notify a newer draft. |
| Submit | Lock the parsed snapshot and stable publication ID synchronously before awaiting work. |
| Publication outcome | Distinguish confirmed success, confirmed rejection, and unknown outcome. End the spinner in each case; only explicit same-ID retry/reconciliation may resolve an unknown outcome. |
| Account change/unmount | Abort supported requests, invalidate all previous ownership tickets, and release private previews/resources. Late replies cannot restore the prior draft. |

This table specifies behavior; it does not require a state-machine library.

### Requests and resources

| Operation | Trigger and termination | Failure/retry behavior |
| --- | --- | --- |
| Initial account/status read | One read per consumer on entry or account change; explicit refresh after a confirmed mutation. Existing focus/Realtime refreshes may be reused with one active subscription. | Finite request deadline; readable retry state after failure. A read never writes status back or starts another read through its own result. |
| Photo selection and upload | One user choice produces one active candidate upload. Validation, success, failure, cancellation, or timeout ends that action. | No upload from a render/effect. Retry is explicit; failed candidates do not discard the working draft. |
| OCR.space read | One explicit click prepares/uploads a derivative and invokes the authenticated endpoint. Provider fetch has a 25-second deadline; the entire read action has a 90-second deadline including preparation/upload/auth/invocation. | Stop at success, error, cancel, timeout, account/photo/type change, step exit or unmount. No automatic retry. Quota/provider/encoding failures allow manual entry. Clear timers/listeners and reject late results. |
| Manual detail validation | Local boundary validation before final review and again on Submit. | Show correctable field errors while preserving the photo and other values. No provider request, timer or network retry is involved. |
| Publication | One Submit acquires a synchronous action lock, snapshots the validated payload, and publishes under one stable ID. | Confirmed success, confirmed rejection, or unknown-outcome feedback ends the spinner. Unknown outcomes retain the ID for explicit reconciliation/retry. |
| Status update after submission/review | A confirmed mutation invalidates its status consumer once; focus/Realtime events may request fresh data. | Deduplicate or coalesce overlapping reads. Fetch results must not themselves call `router.refresh`, publish, or recreate a subscription. |
| Camera and dialogs | Open only from the corresponding user action; cleanup on cancellation, step exit, account change, and unmount. | Release tracks, object URLs, listeners, timers, and dialog focus. Late camera permission results must immediately release their stream when the request is obsolete. |

Before implementation, apply and verify finite deadlines for profile reads, Storage, OCR and publication against the installed SDK's supported cancellation APIs and target environment. OCR's 25/90-second limits are chosen bounds, not a provider latency guarantee. Bound server auth/download work as well as the provider fetch. Do not assume the Auth-only fetch timeout covers them. Use real transport cancellation where supported and invalidate late results in every case; browser cancellation may not stop server/provider processing already underway. A UI-only Promise race does not cancel a write. Keep adapters local to this flow and preserve its authenticated session; never mutate a shared client's transport globally. Manual editing requires no network request.

Every action must release its own loading lock in a controlled finalization path. A stale action must not clear the lock or overwrite state for a newer action. Do not use recursive retries, unbounded timers, blanket `router.refresh()` effects, repeated redirects, or “retry until success” scripts. Normal finite rendering of month/day/year choices is permitted.

On a step transition, close step-owned dialogs and camera resources. Reset focus only on a real transition, not on each render or keystroke. The legacy Profile-anchor handoff uses a single replacement navigation and has no return redirect from the destination.

### Resident-facing failures

Preserve protocol status codes internally for HTTP behavior/test assertions. Map known failures into readable action-specific messages; do not display raw exception text. Use existing inline/notification patterns, with at most one terminal notification per action; field validation can identify each invalid input.

| Failure | Suggested message | Verification requirement |
| --- | --- | --- |
| Invalid image | “Choose a JPG, PNG, or WebP photo up to 5 MB.” | Test empty/undecodable files, MIME mismatch, exact byte limit, and one byte over. |
| Camera unavailable/denied | “Camera unavailable. Upload an existing photo.” | Test denial, ignored prompt, cancellation, and late stream cleanup. |
| Invalid manual details | Show a field-specific message, such as “Enter the full name shown on your ID.” | Preserve the photo/values; require only shared fields/limits. Optional fields may be blank. Field validation does not trigger OCR. |
| OCR unavailable/timeout/key missing or invalid | “We couldn't read your ID photo. You can enter the details below.” | Spinner ends, manual entry stays usable, photo and corrections survive; no raw provider/key errors. Retry is explicit. |
| OCR quota/rate limit | “Photo reading is temporarily unavailable. Enter the details below or try again later.” | No retry loop, paid fallback or draft loss. Do not invent a daily reset/countdown for a shared provider quota. |
| OCR derivative failure/no usable suggestions | “We couldn't read details from this photo. Enter them below.” | Original remains valid for submission; WebP conversion, cap boundary, decoding/encoding failure and empty/partial/over-limit/malformed suggestions are covered. |
| Invalid birthday | “Choose a valid date of birth.” | Test leap days, shorter months, Cancel/clear, fast scrolling, and timezone boundary. |
| Publication not confirmed | “We couldn't confirm your submission. Retry to check the same submission.” | Retain snapshot/ID; do not claim failure/success, allocate a new ID, or start automatic retries. |
| Status unavailable after confirmed write | “Your ID was submitted. Verification status is temporarily unavailable.” | Preserve success and refresh only the status; no second publication. |

Use these messages only for the matching condition. A session/authorization failure must use the existing sign-in/access feedback, not misleading connection copy. Never hide a failure, silently claim success, expose stack traces, or log/display credentials, ID contents, private paths, or signed URLs.
