## F01–F08, U02: selected request contract

Existing Home selects the newest three by `created_at` before considering attention, with only `document_types(name)`. It cannot supply global fee-aware priority or the new card metadata. Select the **minimal read-only security-invoker RPC**, ordered on the server before `LIMIT 3`, rather than arbitrary latest-N/client sorting or unbounded downloads. PostgREST's current column ordering cannot express this joined fee/action CASE and there is no existing Home-priority projection in the inspected migrations. This is an additive retrieval implementation in Phase 1, not a new business action or a model migration performed here.

The RPC must accept no resident ID, use `auth.uid()` ownership plus existing RLS, return no more than three unique requests, and grant execution only to authenticated callers after revoking PUBLIC/anon defaults. Preserve the existing owner-visible request set; do not silently add a deleted-request exclusion that changes Home's current semantics. Join optional catalog/payment metadata without removing rows when a service is retired or unavailable. Migration 0143 supplies owner-requested retired-catalog visibility in source; it is absent from the inspected local policy set. Do not use definer privileges to compensate.

Supported source contracts are legacy requests and `contract_version = 2`, including assessment, fixed, per-page and waiver cases. `requestFee` (`packages/shared/src/lib/service-catalog.ts:120–133`) resolves recorded payment fee first (`document_fee_centavos`, else `amount_centavos`), then v2 assessed amount, else legacy snapshot/catalog. Null means unknown, not zero. Tracking currently chooses a paid payment row, otherwise the first embedded row; that embedding has no explicit order. For the new query/helper contract choose paid first, then newest `created_at`, then ID as deterministic payment ties. Include duplicate historical payment rows in Phase 1 parity tests; do not claim the old unsorted selection is deterministic or refactor tracking here.

Define one attention predicate for both retrieval and Home copy, restricted to recognized open delivery statuses (`submitted`, `in_progress`, `ready_for_pickup`):

- Ready for pickup requires collection, regardless of fee state.
- A confirmed positive resolved fee with payment not paid/waived/refunded requires action only where the existing tracking flow offers payment-method selection (`payment_method IS NULL`) or enabled QR PH (`qrph`, fee ≥100 centavos, settlement flag true). Pickup payment by itself is not an immediate action before collection. Unknown methods/fees must not manufacture a pay action. Pass the existing nonsecret settlement capability as a typed boolean if required for query/UI parity; it must never authorize payment or change RLS.
- `page_count_required` plus pending payment has an existing resident input flow (`ResidentPaymentScreen`, `set_service_request_pages`), and an open paused SLA has an existing Services instruction to review requirements. Include these as attention cases with truthful review/page-count copy, without inventing a new upload/review mutation. Completion/cancellation and unknown delivery statuses never get an inferred action.

Sort attention → other open → completed → cancelled; keep unknown statuses in the non-actionable fallback group with “Status unavailable”, not an invented step. Within each group use `updated_at DESC NULLS LAST`, then `id DESC`. Missing dates remain unavailable. Emit only necessary card/summary, fee/title and history fields. Phase 1 SQL/TypeScript parity must cover all methods, settlement disabled/enabled, below-minimum QR, null/zero/positive fee, paid/waived/refunded, page-count, pause, unknown status and older actionable rows outside the newest three. A supplied capability only affects presentation rank; it cannot grant access or bypass the actual payment screen/server guard.

The verified catalog identifier is `service_kind = 'business'` (`service-foundations.ts:6`; catalog seeds in migrations 0097/0142), whose source name is “Issuance of Barangay Clearance for Business Establishments”. Home's approved short copy is “Business Barangay Clearance”. Unknown/legacy services retain full names unless an exact known catalog mapping is verified. No title filter or guessed UUID is appropriate.

## U01: concrete proposal for separate Phase 1 approval

No expiry field exists in shared schema/types or the inspected local announcement table. Proposed additive contract:

- Add only nullable `alert_expires_at timestamptz`, default null, with no backfill. Null emergency records are ordinary feed posts with unknown advisory lifetime. All old insert/update payloads that omit expiry remain valid.
- DB authority must accept nonnull expiry only for `category='emergency'`, with finite publication/expiry and expiry strictly after publication. Past expiry after publication is valid historical data and displays Expired; it must not be rejected merely because time advanced. Non-emergency plus nonnull expiry is rejected; the form explains clearing expiry before switching category. Do not add an early-end action.
- Shared Zod validation and announcement Row/Insert/Update types mirror that contract. Admin's existing create and edit flows gain one optional expiry input, local-time display/UTC serialization, inline invalid-date/category/order errors, and preserved submitting/auth/audit guards. Create compares effective publication (existing supplied time or captured now); edit compares the existing publication timestamp, since current edit does not change publication. Revalidate on the server; browser conversion alone is insufficient.
- Active Home query: permitted emergency, not deleted, `published_at <= now`, nonnull finite expiry `> now`; order publication then ID descending independently of routine news. Expired rows remain reachable by existing feed/detail ID. A future focused expiry callback must be cleaned up on blur/unmount/scope changes; use existing theme/font/motion preferences.
- Additive order is schema/validation → shared types and compatible publisher → dependent Android loader. Audit impact spans admin create/edit/catalog, Android Home/hub/DRRM/unread/local templates, iOS resident API and resident-web feed/detail readers; see `announcement-consumers.txt`. Do not redesign those clients. Test omitted/null expiry and old payloads, ordinary posts, all timestamp combinations, wrong-scope/guest/admin reads, create/edit audit counts, no duplicate notification fanout and intentional detail-read bridges in a disposable backend.
- Before any authorized target data write, record target/build/schema, row IDs and exact before-values, a restorable backup, and rehearse targeted compensating updates in isolation. No live content was read or modified here. Keep the nullable field on application rollback; do not drop it or blanket-restore unrelated writes. Delivered notifications cannot be unsent. Legacy records remain unpromoted until the publisher reviews them. Approval remains a **Phase 1 model/publisher blocker**, not permission implied by this execution.
