## Decisions (P18-D01…D15)

- **D01 No Home search.** The plan allows omitting it ("make search genuinely work or omit"), and no authorized search source is defined for Home. A08-012 (a typeable search box) is therefore intentionally not built; T02's "no decorative field" holds. If the owner wants search, the sources (services, announcements, help) and the results screen must be specified first.
- **D02 Home composition.** Quick actions match Android and are shown to guests too (each destination asks for sign-in where an account is needed). The labeled Reports counts, the announcement-only bell and the separate inbox entry stay independent contracts.
- **D03 Own Markdown renderer** instead of adding `react-native-markdown-display` (Android's choice): smaller, no new dependency, Dynamic Type and font choice apply, raw HTML never interpreted. Tables are not supported (shown as text).
- **D04 `site_content` holds only Terms and Privacy** (check constraint, migration 0059), so the old "Resident information" screen duplicated them. It was replaced by `/settings/terms-privacy` (R39) and `/settings/about` (R31).
- **D05 Help has no search** (Android has none; the plan says "if displayed"); the category filter runs on the server.
- **D06 Export and delete are screens, not modals**, with a native alert for the format choice, which fits iOS and keeps focus and return paths simple.
- **D07 Export v2 is additive** and requires migration `0135` (it reads `notification_preferences` and `notification_inbox`); deploying v2 without `0135` fails the export for everyone rather than returning a falsely complete file.
- **D08 No local read of the last export time.** The shared generated profile type has no `last_data_export_at`, so the screen learns the cooldown from the server's 429 and `Retry-After`.
- **D09 Deletion matrix = the proposed default of P03-T07 section 3, approved as written on 2026-10-21 (PR-14, decision OD-16).** Erased: household members, request attachments (rows), medical drive registrations, evacuation check-ins, push tokens, notification inbox/events/preferences, announcement read marks, ID submissions no request depends on. De-identified and kept: the profile row, document requests (free text and ID file reference cleared; supporting details emptied) and payments, incident reports (reporter link and photo references cleared), corroborations. Two facts from the real constraints changed the sketch: a version 2 request must keep a verified ID submission (`service_requests_v2_shape`, composite foreign key), so that submission is kept with tombstones instead of deleted; and its `submission_payload` is an immutable snapshot that holds no identity (column comment, migration 0095) and is left alone. The request guard accepts the definer-side edit only under a named operation, so the existing `admin_record_correction` operation is used.
- **D10 Sign-in removal.** Sessions revoked, ban, then a GoTrue **soft delete**. Checked on the local GoTrue (v2.197.0) with a throwaway user: email and phone replaced by opaque values, password cleared, metadata `{}`, identity data and provider id obfuscated, sessions removed, old access token refused by `/user`, password sign-in and refresh refused. The hosted GoTrue version was not checked. Audit-log entries written by Auth at sign-in are not part of this matrix.
- **D11 Apple revocation follows Apple's documented REST flow** (authorization code → refresh token → revoke, ES256 client secret from the key in `APPLE_*` settings). **It has not been run against Apple**: the key material (PR-06) is not configured anywhere, and the Apple documentation pages could not be fetched as rendered text, so the endpoint and parameter names come from the documented API as recalled and need confirming. Without the four settings the function refuses to delete an Apple-linked account (503 `apple_revocation_unavailable`) before changing anything.
- **D12 Freshness.** The first erasure requires an authentication within ten minutes proven by the token (database function); the function does not repeat that check for v2, so a retry after a partial failure can finish what the resident started. An Apple-linked account additionally needs a fresh Apple code.
- **D13 Old tokens.** Writes by a deleted account are refused (tested: a document request and a device registration). Sessions are revoked on the server, so refresh fails. **Gap:** an unexpired access token can still read the rows that are kept (de-identified) until it expires, because PostgREST verifies only the signature. Closing that needs restrictive read policies on those tables or a shorter token lifetime; it is an owner decision, not assumed.
- **D14 Cleanup failures.** Temporary-file purge failure never blocks logout (the files are in the app's cache and are removed again at launch); draft and session cleanup keep their existing fail-closed behavior.
- **D15 Terminal copy.** Only `completed` ends the session and shows the deletion-complete notice. `partial`, `unknown` and `session-ended` say what is and is not known; nothing reports success for a partial result.
