# Admin record lifecycle verification

Implemented in Admin Web for Requests, Transactions, Resident Directory, Incident Reports, Health, Medical Applicants, Households & Residents, and Staff Members.

- Every active row has visible 40px icon-only View Details, Archive, and Delete buttons with descriptive tooltips, accessible labels, distinct colors, and keyboard-focus states.
- Screen-specific row controls retain visible text labels: request processing/pickup/completion/cancellation and Review, incident progress/resolution/unresolved and admin withdrawal for any open or in-progress report in the admin's barangay, medical-registration cancellation, and eligible payment refund/retry. Versioned request buttons use the existing controlled operations and review/payment prerequisites. Archive rows offer the shared details/restore/delete controls.
- Details reuse the Services ContentSideSheet, opening read-only with Edit, Save, and Cancel. Protected request snapshots and collected payment amounts retain existing domain restrictions. Resident ID review remains a separate explicit workflow.
- Each screen links to `/archive/<screen>` with server pagination, search, sorting, details, editing, restore, and permanent deletion.
- Migration `0115_admin_record_lifecycle.sql` provides archive fields, invoker-secured record views and mutations, required tenant permissions, related-record constraint handling, staff self-protection, and household synchronization that preserves archive and check-in state.
- Migration `0116_admin_incident_withdrawal.sql` extends the existing admin incident workflow to withdraw open/in-progress reports regardless of reporter or age. It verifies an active admin and same-barangay access under RLS, locks the selected report, and preserves terminal-state guards and the resident app's separate withdrawal restrictions. `supabase/tests/admin_incident_withdrawal.test.sql` verifies these paths using rollback-only fixtures.
- Migration `0117_admin_request_row_workflows.sql` preserves the existing request RPC signatures while enforcing active administrators, tenant ownership, archive state, row locking, valid transitions and cancellation reasons. Versioned requests delegate to their controlled SLA workflow. Row actions also use that workflow for versioned cancellation and expose pickup collection before completion.
- Request/incident workflows and shared confirmation buttons keep a synchronous lock through prerequisites, writes and verification. Exceptions produce feedback and release the lock. Refund retries now accept failed refunds, reserve the attempt before contacting PayMongo, verify database writes, and retain an uncertain submission as pending to prevent duplicate refunds. Refunds wait for a provider payment ID, and require at least PHP 1.00. No real refunds were issued during testing.

The refund endpoint tests execute the production handler with synthetic database/provider adapters, covering failed-refund retry, simultaneous submissions, permission guards, malformed requests, the provider minimum, uncertain provider responses, failed persistence and early settlement.
- `node apps/admin-web/tests/table-browse/record-browser.mjs`: actual screen components with synthetic records/action adapters. Tests read-only opening, right-side layout, Edit/Save/Cancel, failure feedback and draft preservation, archive list removal, archived details, restore, deletion confirmation and retry, refreshed lists, dark theme, narrow viewport, reduced motion, and Escape/scroll cleanup. Results and screenshots are in this directory.
- `supabase/tests/admin_record_lifecycle.test.sql`: rollback-only PostgreSQL checks against all eight entities, including read-back of saved values, archive/restore, permanent deletion from archives, tenant isolation, resident denial, self-protection, stale changes, related-record constraints, and household check-in preservation. Results are in `database-results.txt`.
- `supabase/tests/admin_incident_withdrawal.test.sql`: all 23 PostgreSQL checks passed for admin withdrawal, persisted status, tenant and active-account permissions, terminal and archived reports, and unchanged resident withdrawal limits. Migration 0116 and the fixtures were tested in a transaction and rolled back; results are in `withdrawal-database-results.txt`. Browser checks also passed for both eligible statuses, older reports from other reporters, failure feedback, and retry.
- `supabase/tests/admin_request_row_workflows.test.sql`: 45 passing PostgreSQL checks for legacy/versioned processing, ready for pickup, completion, cancellation, pickup collection, persisted payment amount/status, legacy fee projections, idempotence, prerequisites, terminal states, archives and permissions. Results are in `request-workflow-database-results.txt`. Together the three database suites passed 221 checks against the combined migrations.
- Expanded browser checks pass on all eight tables and archive views, including thrown/returned failures, detail retries, retained drafts, archive/restore retries, deletion from archives, unavailable records, workflow retries and duplicate clicks. There were no page exceptions or console errors in the fixture run.
- `node apps/admin-web/tests/table-browse/record-e2e.mjs`: all 24 groups passed through a separately built production Next.js app connected to local Supabase Auth, REST/RPC, Server Actions and PostgreSQL. No application data requests were mocked. It verified genuine sign-in/session cookies, all eight screens' saves with independent database read-back, archive navigation, archived details, restores, confirmed permanent deletion, request processing/pickup collection/completion/cancellation, all incident transitions, registration cancellation, staff self-protection and related-record constraint feedback. - The real route test found and fixed an archive entry bug: the server forced `tab=all`, while the browser parsed the active-list default for an unparameterized archive link. This prevented archived rows from rendering and left the view pending. Both now use the same archive configuration, including all-status defaults, dynamic filters and matching search normalization. The eight real archive routes and a regression test verify this fix.
- Changed production files pass ESLint. Full Admin Web type checking passes. The shared resident service form and its component dependencies now use relative imports so the existing legacy Admin Web resident route resolves them in the correct application.
- `npm run build --workspace=@barangayan/web -- --webpack`: production compilation, TypeScript checking, all 39 static-page generation steps and route generation passed, including all eight table screens and `/archive/[screen]`.

The database rehearsal ran against the existing local schema through 0109, temporarily adding 0110–0112 and 0115–0117 within each test transaction and rolling everything back. The Admin Web frontend was built and tested locally; this task did not publish a frontend deployment. Provider responses were simulated in endpoint tests, and no real payments or refunds were issued.
