## Initial feasibility findings and plan discrepancies

For concurrently revised contracts/reachability, apply [the checkpoint supplement](concurrent-source-update.md) first. In particular, local storage results and read-write errors are now observable in the checkpoint, and onboarding no longer exists. The following original observations remain useful baseline/replacement evidence, not a claim that those source branches are unchanged.

1. **AUTH-02:** callback redirects every OAuth failure to static server page `/auth/error`, without a failure attempt ID or a current client outcome consumer. Google linking also uses that callback but deliberately does not queue the explicit-login receipt. A refreshable path alone cannot prove a new failed sign-in. Keep the dedicated alert; no new page/component/server signal is authorized. Safe once-only delivery remains a limitation until an existing permitted client lifecycle can be shown to own this route and a non-sensitive, expiring attempt correlation. Do not assume ordinary `authError` login-query handling covers this route.
2. **AUTH-12–14:** Settings variants exist at `/verify-otp?source=settings` and `/reset-password?source=settings`, guarded by the existing recovery intent/account/session. Repository search found no normal control navigating into the standalone verification route. Dialog sends can establish the intent, and the route then validates it. Retain the route and its tests; do not create a new entry point. Verification success redirects from a server action; the client must not interpret that redirect as failure or assume code after `await settings.verify()` runs.
3. **AUTH-21:** callback success redirects to the same URL as an ordinary Settings visit; failure only adds `emailChangeError=1`, currently consumed by the server page. Existing client props contain current email/profile/pending values but no callback-attempt signal or previous requested address for a new mount. They cannot prove this visit completed an email change. No success on mount, replay from a static query, or backend contract change. AUTH-20 explicit Check confirmation already has the needed requested-address comparison.
4. **AUTH-15/16 and AUTH-18/19:** email helpers turn several SDK/HTTP conditions into plain Error messages. Retain known validation/session/rate-limit guidance. Do not infer structured transport/rejection categories that have been erased. A possibly delivered send with an unclassified failure requires conservative uncertainty wording; exact invalid/expired versus unknown cases need demonstrable evidence without editing shared/server code.
5. **PREF-01–03:** account `.update(...).eq('id', userId)` has no returning selection/count. Error-free resolution does not establish an affected profile row. Use the plan's explicit `Preference applied. We couldn't confirm it was saved to your account.` fallback. Do not add `.select()`, count, or a confirmation read. Controllers apply in memory and hide storage exceptions; later local result handling must make persistence observable at the existing action boundary while leaving reconciliation/logout quiet.
6. **PREF-04:** the Save color handler calls `onAddCustom`, then `onSelect`. Both current ThemeForm callbacks can persist accent to the database. `addCustomColor` also returns a flag set inside a React state updater. This audit does not assume that flag proves committed state. Preserve current operations/counts under the frontend-only rule; one terminal notification must encompass add/select/local storage/account uncertainty. A wider persistence redesign is not authorized.
7. **READ-02–05:** individual hooks discard returned errors; update/delete responses contain no changed-row proof. Existing count refreshes are separate reads and sometimes discard their own errors. Later code can expose the already-returned mutation error locally, but cannot claim exact persisted state on an empty response for a stale/inaccessible entity. No extra verification reads/query changes. Bulk READ-01 has an error-checked upsert; its post-write count refresh must not reverse a confirmed write outcome.
8. **SERVICE-02/04 shared consumers:** admin-web's `src/app/resident/requests/new/new-request-form.tsx` imports resident-web's `ResidentServiceForm` and `VerificationNotice` directly. Resident callers are RequestFormStep, the standalone new-request form, and ServicesVerification. Preserve public signatures/admin behavior and current queries. A path under resident-web is not proof all its consumers are in scope. The mounted/unmounted SERVICE-02 success branches must ultimately have one owner, without retaining parallel delivery. Approved-ID retry returns `Promise<void>` after catching errors; a resolved call does not itself prove approval.
9. **PAY-03/04:** the method picker gates QR PH using `PAYMENT_SETTLEMENT_READY`, but the existing direct QR route mounts the same payment journey; it is not a permission to exercise a real charge. `usePaymongoSource` loses structured creation errors before returning only `status/errorMessage`; source creation may have succeeded before a lost response. Already-paid creation can return `{status:'paid'}` without a QR and is currently treated as missing QR by the hook. Preserve business/network behavior and record this edge; do not turn it into a fresh payment success. A paid status can authorize payment copy, but **receipt ready** additionally requires the existing paid receipt read to succeed; the QR screen does not yet have that receipt result. No extra receipt request is allowed.
10. **LOC-07/EM-03:** rejected map input has click/dragend boundaries, distinct from ordinary map gestures; registration is advisory. Emergency Discard removes the pending fix but **keeps any previous confirmed origin**. Do not say a saved/confirmed location was deleted. Quiet auto GPS, watches, visibility resumes, permission changes, and route refresh remain separate from deliberate requests.
11. **REFRESH-01:** many client retry owners have usable result/error state, but existing server refresh controls expose `router.refresh()`/framework retry, not a read success/error result. Do not toast failure on click, assume void resolution is success, or notify just because an old error remains rendered. See read-retries.md for precise ownership and the cases requiring a demonstrated settled-attempt correlation. Several informational/health views expose no Retry at all; adding one is outside scope.

These limitations satisfy Phase 1's explicit audit exit alternative; they do not mark the corresponding later notification outcome implemented or verified.
