## Exact SQL surface

Every new public operation returns `jsonb`, uses an empty `search_path`, and delegates through the existing public invoker / `barangayan_private` implementation pattern. Revoke default PUBLIC/anon execution on both layers; explicitly grant only the necessary authenticated execution. Every private implementation independently validates current identity, role, profile deletion state, real `auth.users` status (non-anonymous, not deleted/banned), and tenant. No client service-role shortcut. No new role or service.

| Public signature to implement | Input and authorization | Success result |
| --- | --- | --- |
| `public.get_my_household_attendance()` | Active resident only; household is `auth.uid()` | Household read object below |
| `public.lookup_household_for_attendance(p_qr_payload text)` | Active admin; validated household QR; active resident and admin have the same non-null barangay | Same read object, with attendance restricted to the admin's current barangay |

The private implementations have the same names and argument types in `barangayan_private`. This is the verified existing private schema; do not create a separate `private` schema. Read operations do not accept tenant parameters. No names, client timestamps, or actor IDs are accepted as mutation authority.

Use `barangayan_private.household_attendance_receipts` for receipt storage: `actor_profile_id uuid`, `request_id uuid` as the composite primary key, `household_profile_id uuid`, `operation text`, `input_fingerprint jsonb`, `result jsonb`, and server `created_at timestamptz`. Fingerprint is the canonical input object itself, compared as JSONB; no unverified hash extension is required. Store the operation's creation barangay in that canonical object for tenant-bound replay, derived on the server. Reject null request/household/center IDs before mutation. Staff/household references must follow the lifecycle rules below.

The existing roster API remains `public.save_resident_household_if_unchanged(p_members jsonb, p_expected jsonb) returns jsonb`, delegating to `barangayan_private.save_resident_household_if_unchanged`. Its raw expected JSON snapshot is mandatory for meaningful stale-editor protection; an empty/null snapshot means an empty roster, not “skip comparison.” It returns the normalized saved list; `PT409 / resident_household_changed` means refresh and reconcile. Keep existing UUIDs and its role default. Phase 1 must coordinate the mirror and all alternate roster/lifecycle writes before adding historical foreign keys.

### Payloads and result fields

- Household QR text: `{ "type": "household", "version": "1.0", "profileId": "<uuid>" }`. Accept the existing omitted-version household form as legacy v1. Reject an explicitly null/unknown version, non-object/invalid JSON, malformed UUID, center QR, URL, or empty data. Bound **raw UTF-8 bytes to 2,048 before trimming/parsing**; PostgreSQL uses `octet_length`, clients use UTF-8 byte length, not JavaScript string length. Treat data as data; never navigate or fetch a scanned URL. Ignore no authority-bearing extras: reject unexpected keys in the new canonical contract; legacy form permits only `type` and `profileId`.
- Participants: JSON array of `{ "kind": "holder" }` or `{ "kind": "member", "member_id": "<uuid>" }`. Holder is the profile, never an editable roster member. Reject extra keys, invalid kinds/null IDs, mixed households, removed/archived members, empty/null/non-array lists. Limit raw array length to **31**, then deduplicate by kind and canonical UUID. This is the verified conditional-save maximum of **30 additional members plus one holder**. An oversized legacy roster must produce an actionable roster error; never silently truncate it. Extend validation to bypass paths in Phase 1; the current direct JSON/admin writes do not enforce the conditional API's limit.
- Checkout: 1–31 non-null UUID entries, deduplicated and normalized; all must resolve to the same household. Address specific attendance IDs, never “the member's current stay.” Invalid or inaccessible entries abort the entire operation. Do not return the foreign household/center in a denial.
- Household read object: `household_profile_id`, `people`. `people` includes exactly one holder plus the active unarchived roster, with `kind`, `member_id` (null for holder), `name`, `relation` (null for holder), `role` (null when absent), `current_stay`, and `latest_departure`. A stay summary contains `attendance_id`, `center_id`, `center_name`, `checked_in_at`, `checked_out_at`; nullable summaries represent no record. Use stored attendance identity, not a name match. Return at most 31 people; query at most one active stay and one latest closed stay per person, ordered deterministically by time and attendance ID. No unbounded history fetch, staff contact details, or receipt payload is returned.
- Operation receipt: `request_id`, `operation` (`check_in` or `check_out`), `household_profile_id`, `stays`. Each selected stay result contains `attendance_id`, `kind`, `member_id`, `center_id`, `checked_in_at`, `checked_out_at`, and `outcome` (`created` / `already_active` for arrival; `closed` / `already_closed` for departure). Only IDs, timestamps and outcomes go into private receipts; names and contacts are resolved through an authorized read. Replay returns the originally stored operation result, not current mutable projection values. Timestamps are server UTC; clients display Asia/Manila.

### Failure and timeout mapping

These domain tokens are newly defined contracts, not claims about existing SQL exceptions. Mutation validation/domain failures raise an exception so any changes and receipt roll back together. Match only known tokens/codes; never show the raw database message or diagnostic identifier. Use `42501` for identity/access denial, `22023` for invalid input, `PT409` for domain conflict/stale roster. Unknown database/transport failures use the temporary/unconfirmed copy below.

| Outcome token | Plain user message / recovery |
| --- | --- |
| `authentication_required` | “Your session ended. Sign in again.” |
| `attendance_forbidden` | “You do not have permission to register this household.” No foreign details. |
| `invalid_household_qr` | “This is not a valid Family QR code. Scan the household's Family code.” |
| `household_unavailable` | “This household is unavailable. Choose a resident again or ask barangay staff.” Same response for missing, deleted, or foreign household. |
| `invalid_attendance_selection` | “Choose at least one person from this household, then try again.” Refresh selection after a rejected batch. |
| `household_roster_changed` | “The family list changed. Reload it and choose the people again.” Includes unavailable selected members and oversized legacy roster. |
| `attendance_center_unavailable` | “This center is unavailable for arrivals. Choose an active center.” |
| `attendance_active_elsewhere` | “A selected person is already checked in at another center. Check them out first.” Show the current center only after an authorized same-tenant read. |
| `attendance_request_conflict` | “This confirmation no longer matches the original request. Reload before confirming again.” |
| `attendance_lifecycle_conflict` | “Check out active stays before removing this person or changing this household or center.” |
| Temporary read failure | “Could not load attendance. Reconnect and try again.” |
| Mutation timeout / unknown commit | “We could not confirm the result. Retry this confirmation to check its original result.” Keep the original UUID and normalized inputs. Never claim failure/rollback or success without a receipt. |
| Legacy center scan after cutover | “Ask barangay staff to scan your Family QR and confirm who is present. Update the app if needed.” Do not queue or imply official attendance. |

Use the existing 15-second deadline pattern for new requests, with no automatic mutation retry. A deadline ends busy state and disregards stale reads. Retry is explicit and keeps the operation key; permission/tenant checks still run before receipt replay. A definitive invalid-input response may discard the attempted selection/key only when the user deliberately changes it and starts a new operation. Never retry a changed batch under the previous UUID.

## Transaction, lock, and access contract

1. Serialize `(staff profile UUID, request UUID)` across **both operation kinds**, then lock the household profile, relevant center rows in UUID order, and attendance rows in UUID order. For checkout, an initial non-locking lookup may discover the household/centers, but revalidate every row after acquiring ordered locks. Unique active-stay indexes remain the final guard.
2. Check current authenticated actor and tenant before replay; recheck relevant actor/household/center authorization under the mutation locks. Receipt access requires the stored operation barangay to equal the actor's current barangay, even if the household and actor were both later reassigned together. Use database identity at transaction execution, not JWT role/tenant claims or an earlier lookup. Concurrent lifecycle cases need explicit database tests; Phase 0 does not assert an untested revocation guarantee.
3. Receipt key is `(actor_profile_id, request_id)`; its immutable canonical fingerprint includes operation, household, center where applicable, and sorted deduplicated participant/attendance IDs. Include no supplied names/tenant/timestamps. Same key/different normalized input rejects. Receipt and stays commit or roll back together. Keep receipts for the retained household lifecycle; no TTL pruning that would let a delayed arrival reopen a visit.
4. Roster-only writes and household archive/reassignment start at the household lock. Center-only archive/reassignment locks its center, checks active stays, and never later acquires household locks. Arrival rechecks center state/ownership after acquiring that lock. Preserve the existing conditional-save advisory key (seed 1) when coordinating compatible callers, and document the relation between that key and the household row lock. Do not acquire it after a conflicting member lock.
5. The present generic admin mutation locks a member before its profile. Phase 1 must change this ordering for **all** household save/archive/restore/delete branches and direct/trigger-backed paths before concurrency testing. A trigger taking the household lock only after its UPDATE already locked a member is insufficient; remove or route that direct write surface. No resident/admin direct attendance writes remain.
6. Enforce one active holder stay per household and one active member stay across centers, using two partial unique indexes with `checked_out_at IS NULL`. Add the member/household composite FK backed by `(id, profile_id)` uniqueness, departure time/actor pair and chronological checks, non-null arrival actor/time, and non-cascading references for retained member/center/actor history. Existing legacy indexes/booleans do not establish these invariants.
7. Enable attendance RLS and revoke direct client mutation grants. Resident SELECT follows `household_profile_id = auth.uid()` with an active resident identity, including history retained from a previous barangay. Admin SELECT additionally requires the row's immutable `barangay_id` to equal the admin's **current** barangay and allowed current household ownership. Private receipt table belongs in `barangayan_private`, has no direct anon/authenticated table access, and uses RLS as defense in depth; replay is only through validated operations.
8. Resident/center barangay reassignment is blocked during any active stay. Closed rows keep their stored barangay. New-barangay admins cannot see old-barangay attendance through lookup, projection, errors, or receipts. On a renamed/archived center or member, history keeps stable references. Inactive/archived centers still allow checkout; archived/deleted households cannot receive new arrivals. Household archival with active stays must be rejected so checkout is not stranded.

The lock order is a required cross-writer contract, not a claim that today's implementation follows it. Phase 1 needs two-connection tests for arrival/removal, center archive/reassignment, household/actor reassignment, revocation/replay, and conflicting centers.

## Erasure, export, and compatibility decisions

- Keep referenced staff profiles as de-identified rows. Existing v1 erasure anonymizes a profile and bans Auth; local v2 additionally soft-deletes Auth and records resumable state. Neither requires physically deleting an actor. New actor FKs must restrict hard deletion; do not use actor `SET NULL` or cascade that loses another household's attendance. Staff roster deletion currently deletes `barangay_officials`, not the referenced profile.
- Erasing a household deletes its attendance and receipts **before** clearing `profiles.household_members` or deleting canonical members. Coordinate this with the household lock in **both** `request_own_account_deletion()` and `erase_own_account_records()`. Remove receipts owned by an erased actor; keep attendance of other households with its de-identified actor reference. Do not weaken existing fresh-authentication, ID/evidence, or deletion state guards. Retry after erased identity must be denied, never recreate stays.
- Removing/archiving an active member fails clearly. Once closed, remove the member from the editable JSON and archive a historically referenced canonical row; hard-delete only unreferenced removed rows. Renames preserve IDs. Direct hard deletion of referenced centers/members/profiles fails; use archive/de-identification as appropriate. Restore must retain IDs, tenant boundaries, roster limits and history.
- Both export versions need the resident's attendance history, including archived-member visits and previous barangays. Use paginated owner-scoped queries. Residents cannot directly read private staff receipts; export uses a narrow authorized projection of their household's receipt metadata (IDs/operation/times only), with no new public RPC beyond the four above. The existing authenticated export Edge Function may use a service-role read **only after verified caller identity and a strict caller-derived household filter** for that private section. Keep service credentials server-side and do not grant residents receipt table SELECT. If this cannot be secured/tested, A13 stays blocked. Local v2's section contract and the iOS export section labels must include these sections; v1 adds fields compatibly without dropping existing fields. Never silently return a partial new attendance section as a complete export.
- Do not backfill active stays from legacy booleans or scan events. Retain `evacuation_center_checkins` as legacy history. Member compatibility fields are transactionally derived from authoritative stays after cutover and inaccessible to arbitrary table/generic record mutations.
