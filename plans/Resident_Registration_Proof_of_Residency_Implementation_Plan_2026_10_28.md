## 1. Outcome, scope, evidence labels

**Outcome.** A resident who registers by email/OTP (not Google) submits a government ID as proof of residency in Ampid 1, during account setup, using the **existing** ID-capture wizard and evidence pipeline (`publishIdEvidence`, `id_submissions`, `profiles.id_verification_status`) rather than a new one. Registration still completes in one sitting; verification status gates **feature access** through gates that already exist, not account creation. Staff review through the **existing** admin-web `ResidentIdReview` — no new review UI is built.

**In scope**
- New required step in `account-setup`, reusing the Settings → Valid ID wizard's steps via one extracted shared component.
- New `setupRoute.destination` (`id_verification`) placed between `details` and `password` in `resident-account-setup.ts` / `setup-navigation.ts`.
- Resubmission rate limit (1/60 min, D4) on "Submit a replacement ID," which has none today.
- Push notification on staff decision, reusing existing plumbing unchanged.
- Verification (not construction) that the existing per-feature gates and `ResidentIdReview` correctly handle a registration-sourced submission.

**Out of scope**
- Any new admin-web review UI or access-gate component — both already exist (4.3).
- Retroactive ID verification for pre-existing residents (D1).
- OCR/extraction changes — `extractIdDetails` reused as-is.
- Google-sign-up residents — unaffected (only the `email_otp` branch of `resident-account-setup.ts:92` is touched).
- ID evidence storage convention, bucket, encoding, or retention policy (D3) — unchanged.
- Any related problem noticed but not required for this outcome — logged in the final execution report as found, not fixed.
- **Optional improvement, kept out of scope:** `apps/resident-web` already has its own equivalent Settings → Valid ID flow and action-guard pattern (`resident-action-guard.tsx`, `valid-id-flow.tsx`), and `apps/resident-ios-mobile` has only a stub reference (`features/services/readiness.ts`) under its own separate, already-tracked phase plan. Neither is touched here; registration-time mandatory ID submission for either platform is a candidate follow-up, not part of this outcome.

## 4. Design

### 4.1 New setup destination

`packages/shared/src/lib/resident-account-setup.ts:101` currently does:
```
if (!status.profileComplete) return { destination: 'details', required: true, returnTo: 'home' };
if (status.passwordSet === false) return { destination: 'password', required: true, returnTo: 'home' };
```
Insert between them:
```
if (status.registrationOrigin === 'email_otp' && !status.idSubmitted) return { destination: 'id_verification', required: true, returnTo: 'home' };
```
`status.idSubmitted` is a new derived field (true once `current_id_submission_id` is set), computed the same way `profileComplete`/`passwordSet` already are. Google-origin residents skip this branch entirely — matches the existing `registrationOrigin === 'google'` short-circuits already in the file.

`setupAllowsApp`/`setupDestination` in `setup-navigation.ts` need a matching branch — `id_verification` is **not** added to the "always allowed" list, so the root navigator keeps a resident on `account-setup` until they've submitted (not until *approved*; approval is handled by the existing access gate in 4.3).

**Affected consumers, verified:** every other reader of `route.destination`/`setupRoute.destination` branches on string equality with a graceful fallthrough — `account-setup.tsx:55-68` (early returns, then an `AccountSetupStatus` catch-all), `setup-navigation.ts:4,9-10`, and `auth/callback.tsx:42-46` (reads only `status_loading` plus the *path string* `setupDestination` resolves to, never the raw `id_verification` member). There is no exhaustive switch anywhere on this union, so adding a new destination value is additive and does not require touching `auth/callback.tsx` — **verified fact**, not an assumption, confirmed by reading all four call sites this pass.

### 4.2 Account-setup screen wiring

`account-setup.tsx:58-65` gets a third branch alongside `details`/`password`:
```
if (route.destination === 'id_verification') return <ResidentIdCaptureStep ... onSaved={...} onBack={...} />;
```
`ResidentIdCaptureStep` is the **existing** 4-step wizard body from `valid-id.tsx` (type → photo(s) → confirm details → submit), extracted into a shared component so Settings and registration render identical steps instead of forked code. The wizard's internals, validation, upload path, and `publishIdEvidence` call are unchanged; its existing single-flight guard (`busyRef`, `publication.current` signature-dedupe, `valid-id.tsx:208-222`) is inherited verbatim, so no new concurrency risk is introduced by reusing it in registration.

On successful submit, `onSaved` calls `setSetupIntent('sign_in')` (consistent with `savedDetails`/`savedPassword`) and `refreshCompletion()`, advancing the route to `password`.

### 4.3 Access gate (pending/failed) — nothing new to build

Per D2: `services/index.tsx:72-88` shows a "Verify Now" card whenever `idVerificationState(profile) !== 'verified'`; `[documentId].tsx:50,123` / `charter-request-form.tsx:168,365` block document requests until verified. Because registration writes through the same `publishIdEvidence` call into the same `profiles.id_verification_status` column, a resident who registers and is `pending` sees this existing behavior with no new code.

The only new piece is the **resubmission rate limit** (D4: 1/60 min) on "Submit a replacement ID" (`valid-id.tsx:245`), which has no cooldown today.

### 4.4 Admin-web

No code change expected. `ResidentIdReview` reviews "the current evidence version through the same RPC" regardless of submission origin — registration-time and Settings-time evidence are identical rows through the same write path. The RPC/authz boundary staff actions go through is unchanged by this plan (no new write path is introduced on the staff side), so no new security surface is opened there. Phase 4 verifies this; it does not build it.

### 4.5 Database

One candidate migration (`0145_resident_registration_id_verification.sql`, next free number after `0144`):
- Adds nothing to `id_submissions`/`profiles` schema — those columns already exist (`id_verification_status`, `current_id_submission_id`, `id_repair_required`; `database.ts:1253`, `service-catalog.ts:74-88`).
- Open question, resolved at Phase 1: whether `resident-account-setup.ts`'s `status.registrationOrigin` is sourced from a real column end-to-end, or only exercised in its unit test (`resident-account-setup.test.ts:29-33`) with a hand-built fixture. The test proves the *type* exists, not that the *production data path* populates it for every signup method. If it's already wired, no migration is needed at all.

#### Phase 4 addendum — server guard and rejection retries (owner-approved), 2026-10-28
- **Why.** Decision (2) above left the limit client-only; the owner then asked for a server guard, and then for retries after rejection: the resident may retry at once after a rejection, the third rejection in a row locks submissions for an hour, and the cycle repeats. This supersedes decision (1) and adds a migration beyond the single one section 2 allowed. Scope: Android only; no resident-web or iOS code was touched.
- **Rule (owner-chosen: lock after the 3rd reject; pending or verified replacement stays 1 per 60 min).**
  - First submission: never delayed.
  - Latest version pending or verified: the next version needs 60 minutes since that version's `submitted_at`.
  - Latest version rejected (`verification_failed` or `revoked`): retry is immediate, unless the number of consecutive rejections since the last non-rejected version is a multiple of 3 and the staff decision (`reviewed_at`) is under 60 minutes old. Because the count carries on, the 6th, 9th, ... rejection lock again.
  - A lost-response retry of the same submission id returns before the check and stays idempotent. The profile row lock serializes concurrent submissions.
- **`supabase/migrations/0150_id_resubmission_rate_limit.sql`** (next free number; `0148`/`0149` belong to other sessions; not pushed anywhere, so it was rewritten in place). It patches the live `barangayan_private.publish_id_submission` the way `0118` does (`pg_get_functiondef` plus `replace`, failing loudly if the anchor is missing) with one block before the version lookup. The error is `id_resubmission_rate_limited` (SQLSTATE `54000`) for both cases. Grants and the public wrapper are untouched.
- **Android only.** `src/lib/id-resubmit-limit.ts` mirrors the rule from the resident's own `id_submissions` rows (`version, decision, submitted_at, reviewed_at`, existing own-row select policy). `use-id-resubmit-limit.ts` loads them, reloads when the profile's ID status changes or after a submit, keeps the last result while reloading, and starts the hourly window locally after a submit until the next load includes it. `valid-id.tsx` disables "Submit a replacement ID" with a countdown for pending or verified, shows "You have used all 3 attempts.
