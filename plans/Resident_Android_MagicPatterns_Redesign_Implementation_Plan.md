### Scope and quality contract

The required outcome is the exact reference screen and animation reproduction defined above, with existing behavior and settings preserved and every necessary adaptation recorded. “Clean,” “fully working,” and “production level” are acceptance objectives, not assurances that can be proved by a plan or by clicking a prototype. A successful review must cite the tested build, state, environment and result; unresolved failures or untested integrations must remain visible.

- New product features, backend work, routes, user settings, datasets, integrations, broad error-handling rewrites, and unrelated refactors remain excluded. Re-expressing a reference control around an existing action is allowed presentation work; inventing an unsupported action or changing its rules is not.
- Do not copy prototype fixtures, identity/medical sample records, transaction references, locally simulated success timers, or demo business rules into application code. Do not copy the prototype's React/Tailwind architecture into React Native.
- Use existing components first, then small opt-in variants. A new helper must remove actual duplication or implement a necessary reference presentation; generic frameworks and parallel old/new screen implementations are excluded.
- Do not add dependencies, edit backend contracts, hide errors, suppress warnings to pass a check, lower assertions, or change query/poll/subscription behavior as a shortcut. Handle unexpected existing failures by recording the baseline and their affected acceptance criteria.
- Existing error identifiers belong in appropriate diagnostics where already available; resident-facing errors should use the app's clear messages and recovery controls. “No error codes” does not mean hiding failures or manufacturing success.
- Delete replaced, genuinely unused presentation code after its replacement passes the stated checks. Do not retain duplicate implementations as permanent fallback. Unreferenced status cannot be assumed from a text search alone, especially for file-based routes and dynamic assets.
