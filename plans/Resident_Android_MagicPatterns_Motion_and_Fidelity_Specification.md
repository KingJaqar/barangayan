Evidence labels used here:

- **S:** inspected v32 source declaration; timing values are configured values, not observed execution durations.
- **I:** interaction/final state reached; selected fresh intermediate samples now exist as mapped in the capture index. Continuous smoothness remains unverified.
- **P:** proposed Android acceptance target or adaptation, not implemented or tested.
- **U:** unverified live variation, native behavior, or performance.

Use source-specific values where declared; use the breakdown only to fill a genuine omission and label it as a proposed choice. Do not replace all source timings with a universal 200 ms fade. `E` below means cubic bezier `(0.23, 1, 0.32, 1)`. CSS transitions without a declared easing retain unspecified/browser-default easing in the evidence; they are not proof of `E`.

## Visual fidelity acceptance

The target is the closest faithful reproduction allowed by existing behavior/settings/native constraints, not a generic restyle. For each of the 39 entries, maintain a screenshot pair or explicit missing-state entry and link its motion IDs where applicable.

1. Compare matching fixture/state at the same logical content width, excluding the prototype's simulated phone/status chrome. Capture top, scrolled content/footer, expanded/selected state and any changed busy/error/empty state. Record content differences, not an unexplained percentage score.
2. Use source/breakdown geometry as declared targets; for nominal 400 dp width propose a maximum 2 dp unexplained error for major edges, paddings and indicator alignment after accounting for platform insets. This is a new review tolerance, not a measured current result. Repeated spacing/panel inconsistencies fail even if individual edges fit that tolerance.
3. Match hierarchy, grouping/dividers, content density, corner shapes, icon placement, chips, card widths, sticky elements and action placement. Verify 320, 360 and 400–412 dp plus short-height/keyboard states. Critical labels/content must not clip at supported font scales; document wrapping/native typography differences instead of shrinking text to force a match.
4. Preserve actual selected fonts/accents and admin-managed content. Figtree, exact Lucide silhouettes, unspecified dark-reference surfaces, native dialogs/switches/map tiles and existing stack transitions are documented adaptations in the main plan. No hardcoded reference green/white or fixture content may bypass settings or live data.
5. Provide light/dark and representative default/blue/warm/custom-extreme accent evidence for every major family; all offered font choices on shared controls and long-content examples. Include TalkBack focus/role/selected/disabled states, sufficient contrast, non-color status cues and reachable hit areas.

## Motion, accessibility and performance acceptance

These checks are **planned, not run**. MuMuPlayer is primary; use explicit ADB serials and known build/density/refresh rate. Docker is optional for existing isolated fixtures; Brave/browser automation is approved for prototype inspection and necessary resident/admin web regression checks. Web results supplement, never replace, native evidence.

- Record each adopted ID at normal speed and reduced motion; use original-speed video for perceived continuity and frame inspection for timing. A source value is not a measured native duration. On isolated timing tests, propose ±max(2 captured frames, 10%) tolerance for explicitly timed segments; report missing/low-rate capture as unverified. Browser-native scroll/spring/OS transitions have no invented fixed timing requirement.
- Use the measured display refresh interval as frame budget (about 16.7 ms at 60 Hz). After warm-up, repeat ten transitions on the same fixture/build; retain recordings and available JS/UI profiler/frame data. Target at least 95% within the device frame budget and no repeatable stall over 50 ms attributable to the change. These are proposed review gates, not current measurements; a recording alone cannot prove internal frame timing. Missing profiler evidence prevents a measured performance claim.
- Compare baseline and candidate on the same MuMu configuration, with debugger/profiler overhead noted. Check one cold navigation separately for image/map/font loading. Emulator performance cannot establish physical-device performance; record that limitation for release decisions.
- Under reduced motion: remove translations, scaling, rotating interpolation, decorative pulse and smooth programmatic scrolling; allow only an optional opacity fade of at most 100 ms. Apply immediately or on the next explicit action when the system setting changes, with no route remount. Sheets/dialogs must remain operable. This stricter native fallback is an accessibility adaptation, not a claim that every prototype component implements it.
- Reverse/reselect during entry/exit five times, close via existing close/backdrop/handle/Android Back where supported, open keyboard, rotate or resize where currently supported, background twice and return. Final selected item, route, scroll position and controller state must be correct; no ghost scrim, invisible touch blocker, stale callback, duplicate card or stranded camera.
- Animation completion may update presentation cleanup only, never submit/pay/delete/register or change business state. One action retains its existing request/mutation sequence. Do not delay guards or expose disabled actions until an animation completes.
- After closing/unmounting/blur, compare timers/listeners/channels/camera/location and request counts against the same baseline route. No added resources, repeated layout updates, polling, geocoding or map-fit feedback caused by the presentation change. Decorative loops are allowed only while their intended state is visible, and must stop on reduced motion; unintended execution loops are never acceptable.
- Run the main plan's lint/type/unit/contract/export checks appropriate to owned files; do not manufacture tests for style constants or weaken existing assertions. Preserve visible loading/errors/retry/cancel. Any new runtime error, unexplained failing check, inaccessible content or functional regression blocks that packet.

## Remaining limitations and decision rules

No animation is certified smooth yet. Prior walkthroughs establish selected interactions/final states; this revision establishes source values, fresh sampled motion captures and implementation/test targets. Selected browser movement is visible in the evidence, but high-rate continuous playback, reduced-motion reference behavior, native baseline, all MuMu acceptance and integrations remain unverified. In fresh direct-center-pin selection, the final card was absent, while list-row selection reached the expected card; do not copy this result as intended behavior or treat it as an Android bug. The capture index preserves both observations.

If exact appearance/motion conflicts with existing functionality, preserve behavior and log the smallest explicit adaptation with before/reference/proposal/evidence. If it requires a backend/API/query/permission rule change, leave that element out of implementation and document the limitation. Do not silently simplify motion, promise pixel identity, hide failures or claim a bug-free/production-ready result from this specification.
