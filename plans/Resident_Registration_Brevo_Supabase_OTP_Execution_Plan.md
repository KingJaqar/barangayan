## 2. Confirmed product behavior

### Email registration

1. **Email confirmation:** enter email, choose **Send code**, enter the six-digit code, and choose **Verify and continue**. Support change-email, resend, a 60-second resend countdown, invalid/expired-code feedback, backend rate limits, delivery errors, loading, and retries.
2. **Personal details:** enter first name, last name, middle name, suffix, sex, date of birth, mobile number, House No., Street, and Employment Status. Show the verified email read-only. Show Barangay **Ampid 1**, City **San Mateo**, and Province **Rizal** read-only, supplied by the existing configured registration locality. Keep the existing optional occupation and location-map behavior. Choose **Next** to validate and save the details.
3. **Create password:** enter password and confirmation; choose **Create account**. Set the password on the account established by OTP, refresh setup status, and route to Home using the verified session. Do not call `signUp` again or sign out after success.

All current required personal fields remain required. Middle name, suffix, and occupation retain their existing optional rules. Preserve existing name, mobile, birth-date, password, and map validation. Back navigation within the wizard retains entered values. Passwords, OTPs, and unsaved personal details are not written to Android AsyncStorage.

Supabase creates an unfinished Auth account during step 1 and establishes a session after successful OTP verification. This replaces the earlier account-at-final-step proposal. Never infer that OTP was entered from `email_confirmed_at` alone when automatic confirmation is enabled. UI advancement requires a successful verified session.

Once an email has been verified, changing it means signing out of that setup session and restarting verification; do not change the existing account's email through the registration wizard. Explain that an unfinished account may remain. Do not automatically delete abandoned accounts as part of this feature.

### Google registration

## 3. Technical decisions and compatibility

### Shared interfaces

Add a shared `ResidentAccountSetupStatus` contract containing `registrationOrigin` (`email_otp`, `google`, or `legacy`), `profileComplete`, `passwordSet` (`true`, `false`, or `null` when legacy provenance is unresolved), and `hasGoogleIdentity`. Backend values describe the authenticated caller only. An unknown legacy password state is not equivalent to unset: do not offer credential replacement through first-time setup. A pure shared routing helper selects the required email step, optional Google setup, or Home from status plus explicit navigation intent. Model transport/loading/errors separately from account status; a failed RPC must never become `passwordSet: false` or `profileComplete: true`.

Add `get_resident_account_setup_status()` as an authenticated RPC with no user-ID, tenant, role, or password parameters. Keep privileged Auth reads in the private schema, with an explicit caller check, fixed search path, minimal grants, and no anonymous execution. Return no hashes, credential material, or other users' data. Reuse the existing completion rules; shared validation and the backend's completeness result must agree.

Use `signInWithOtp` for sending and `verifyOtp({ type: 'email' })` for verification. Resend uses the same normalized email and supported Auth operation; a successful send is not a verified email. Enforce the 60-second UI cooldown and respect stricter backend limits. Reuse the hosted OTP expiry rather than silently changing expiry for recovery/invitation/email-change flows. Use the existing profile-completion operation and Supabase Auth password update instead of inventing a second OTP service or creating another account.

### Password provenance and migration

Introduce a private, server-maintained lifecycle record keyed by Auth user ID. Initialize newly created accounts from this feature's email-OTP registration marker as password-unset even if Supabase has generated an internal temporary hash. Capture the origin at creation; later edits to user metadata cannot replace origin or password state. The initial marker is a flow-classification hint, not a trusted authorization claim. Resolve Google identity from Auth-managed identities, not editable metadata.

Backfill existing account password availability from known existing authentication behavior and stored credentials, with tests covering password users, Google-only users, and linked accounts. Before backfill, inventory whether any earlier passwordless accounts already contain generated hashes; do not label an unknown temporary hash as a resident-chosen password. Inspect the deployed Auth behavior and keep unresolved legacy provenance explicitly unknown until valid existing-password authentication or a real password update provides supported evidence. Such users retain current-password change/recovery options and their existing credential; they are never treated as a new passwordless signup.

Observe actual Auth password changes server-side so first setup, change password, and verified recovery all update the lifecycle record. Do not accept client-written `passwordSet` flags. Prove that OTP creation, resend, token refresh, Google linking, and metadata updates do not falsely mark a password as chosen. Status reads and repeated callbacks must be idempotent and preserve existing records.

Use the next unused four-digit migration prefix after the highest repository prefix. This execution used `0107`, `0108`, and `0109` (Phase 3 added no migration); the highest repository prefix at this reconciliation is `0109`, so the next new migration would be `0110` only if still unused when work begins. Never renumber pushed migrations. Keep migrations additive and compatible with existing clients. Regenerate/update shared database types and test RPC grants/replay. The status record follows established deletion/anonymization rules without retaining credential material. The explicitly approved repair of 0109's newly generated hosted history record is a recorded one-time exception, not permission to alter earlier migration history.

### Sessions, errors, and recovery

Keep OTP/recovery/Google-sign-up navigation intent separate so the new flow cannot hijack password recovery or account linking. Android protected navigation must wait for session and setup status before choosing a destination. A status error presents retry/sign-out rather than assuming completed setup.

Persist only the existing supported session and minimal non-sensitive navigation intent. After Android restart, reload saved profile/setup status from the server. If a session has expired, require authentication again and then resume; never reuse an OTP/password from storage. Unsaved entries may be lost on a restart, while successfully saved details remain intact.

Preserve the existing duplicate-callback protection and same-origin/scheme redirect validation. Reject malformed, expired, replayed, or unsafe callback destinations. Do not trust a locally set “reauthenticated” flag or provider list as proof of fresh Google authentication. Validate the newly completed authentication session and same account before a first-password write. Verify the actual Supabase secure-password-change behavior and nonce handling; do not claim client current-password checking changes Auth's server-wide guarantees.

On timeout or a dropped response, reload server state before repeating a write. Profile saving and password updates are separate operations: if details save but password setup fails, resume the password step rather than clearing details or creating another account. Disable repeated submissions while pending, bound network waits, and keep success navigation dependent on confirmed persisted results.

### 3.2 State model and routing contract

Use one typed coordinator rather than competing screen redirect effects. Transient states include session restoration, status loading, email entry, code entry, verification, profile editing/saving, password editing/saving, Google pending/exchange, recoverable failure, and completion. Keep the pending request separate from the current step so a failure retains the resident's entries.

| Authoritative condition or intent | Required Android destination/behavior |
| --- | --- |
| Session not restored yet | Keep existing startup loading/splash behavior; show neither Home nor signup prematurely. |
| No session, email signup | Email step or pending-code step for the current attempt; send success cannot unlock profile/password. |
| Recovery session or explicit recovery intent | Existing password recovery screen takes precedence; it must not enter the registration wizard. |
| Authenticated status loading/error | Bounded loading followed by retry/sign-out; never grant completion or invent a password state. |
| New `email_otp` account, profile incomplete | Required personal-details step, even when the app has restarted. |
| `email_otp` account, complete profile, password unset | Required password step; no Google skip controls. |
| Completed account after OTP | Home, preserving account ID and credential. |
| Google sign-up intent, incomplete profile | Details step with the explicit skip option. Ordinary Google sign-in may enter Home with warnings. |
| Google details just confirmed, password unset | Optional password step; skip goes to Home. |
| Google details confirmed, password already set | Home; no password overwrite. |
| Google profile complete, password unset, ordinary returning sign-in | Home with Set Password warning; no repeated wizard. |
| Linked Google on an unfinished email-origin registration | Preserve immutable origin and required email setup; linking cannot erase outstanding required setup. |
| Legacy password provenance unknown | Preserve existing login behavior; show Manage Password/recovery guidance rather than first-time creation or a false Password not set warning. |
| Settings profile/password intent | Open the requested independent Settings action, then return to Settings on success; never accidentally re-enter signup. |
| Guest browsing | Preserve existing read-only guest behavior; a signed-in unfinished email setup cannot use guest state to escape its required flow. |
| Staff, banned, or deleted account | Existing authorization/error behavior; do not provision a resident or enter its wizard. |

Bind pending requests, status/profile caches, and callbacks to the current user and attempt ID. After logout, cancellation, email change, or account switch, discard sensitive entries and pending destination/reauth state. Ignore late results from an older user/attempt. A legitimate email-origin account later linked to Google keeps its origin; Google identity and login method are separate facts.

Step transitions depend on confirmed results: verified session for step 1, committed complete profile for step 2, successful Auth password write plus refreshed setup status for step 3. Replace the completed wizard in history so Android Back cannot reopen a consumed OTP or resubmit password creation. Before completion, Back retains personal entries within the same mounted setup and never downgrades server-confirmed progress. Leaving email setup offers a clear way to cancel/sign out; there is no email Skip button.

### 3.4 Requests, cooldowns, and interrupted writes

- Use one in-flight operation per action and an attempt ID to prevent double sends, verification, profile writes, password writes, and browser launches. Ignore stale responses after unmount/cancel/account change. Disable dependent actions while saving; Back/cancel cannot launch a competing mutation.
- Compute the resend countdown from a deadline, not a decrement-only interval; recheck on AppState resume. Keep a minimal email-free cooldown deadline across a restart to avoid immediately encouraging another send. A rejected request must not show “Code sent.” Backend rate limits remain authoritative even after reinstall or clock changes.
- Default request watchdog: 30 seconds for send/verify/status/profile/password actions, with no automatic resend or password retry. An expired watchdog ends the spinner and presents a recoverable pending/unknown result. A UI timeout is not proof a server mutation was cancelled; avoid overlapping retries until the result is reconciled or the transport has completed/aborted safely.
- Retry safe status/profile reads with bounded backoff; do not retry invalid OTP/password failures automatically. Respect provider rate-limit/retry information when present; otherwise show an honest waiting/retry action rather than inventing an exact server reset time.
- After an ambiguous profile save, refetch persisted profile and compare the submitted fields before retrying. After a password response timeout, reload lifecycle status; do not use `passwordSet: true` alone as proof that a particular new password succeeded when one already existed. Resolve through a supported authenticated password check or explicit reauthentication/recovery, never by reporting unverified success.
- Password/OTP fields live only in memory and are cleared after success, account change, cancellation, or screen disposal. Successfully saved profile fields survive process death; unsaved entries may require re-entry. App restart cannot rely on old in-memory flags or a persisted “completed” boolean.
- Subscribe/unsubscribe to Auth and AppState correctly. Keep Auth event callbacks lightweight and perform RPC/network work outside the synchronous Auth callback to avoid lock/deadlock issues. Deduplicate user/token events so token refresh does not repeatedly provision a profile or reopen onboarding.

### 3.5 Password provenance, migrations, and authentication proof

The implementation must prove its tracking design against the deployed Auth version before new screens ship. Do not derive chosen-password state solely from `encrypted_password IS NOT NULL` or editable metadata. Lifecycle records use a user-ID primary key, immutable origin, explicit password provenance, and server timestamps; store no password/hash copy. Put functions/tables in the existing private schema, leaving only the narrowly granted caller RPC exposed. Inspect the deployment's supported Auth trigger permissions; do not create custom functions/tables in Supabase-managed schemas.

Build transaction-level tests for user creation with a generated OTP password, subsequent OTP sends, actual password setup, change, recovery, identity linking/unlinking, and metadata changes. The observer must recognize user creation separately from later password writes and account for Auth's real statement order. If automatic temporary-password changes cannot be distinguished reliably, replace the observer with a supported, verifiable design before progressing; a client flag or untested hash-change trigger is not an acceptable fallback.

Backfill is a reviewed data migration with per-category counts and an explicit unknown category. Prove replay does not overwrite known chosen passwords or immutable origins. Use unique constraints/atomic conflict handling for concurrent callbacks; do not perform unsafe read-then-insert provisioning. Trigger failure must roll back consistently and surface an actionable error without leaving a half-created identity. Test fresh installation and upgrades from representative existing state. Shared types and RPC response shape must agree, and permissions must be tested through actual REST/RPC callers as well as SQL.

For Settings first-password setup, require a newly completed Google authentication tied to the same intended Auth user, purpose, and unexpired attempt. A five-minute application reauthentication window is the default; it does not replace Supabase's own secure-password-change rules. Provider membership, `last_sign_in_at`, a refreshed token, or a locally written timestamp alone is not sufficient proof. Determine which signed session/AMR/authentication timestamps and nonce requirements the deployed provider/SDK actually support, then test those assumptions. Reject a callback for another account, clear that unintended session, and require the original resident to authenticate again; do not silently operate as the switched user.

Retain current-password verification for existing password changes. Verify the returned user ID matches the intended account before writing. If reauthentication changes session ID, update the coordinator to the newly verified same-user session without interpreting it as signup.

Document exactly which requirements are enforced by the Android flow, Supabase Auth configuration, and any server endpoint. The existing `updateUser` and deletion endpoints must be tested directly: a custom Android reauth screen alone cannot make their backend enforce fresh Google authentication. If a server-enforced fresh-auth guarantee is required, prove it with the supported Auth policy/endpoint and negative direct-request tests; do not bypass it with an Admin API accepting a client “reauthenticated” flag. Unsupported enforcement is a phase 1/3 blocker to resolve, not a production security claim.

Deleting/banning an account does not alone prove all old access JWTs are unusable. Keep existing deleted-profile submission guards, clear Android session/caches, and test rejected sensitive actions using an older token after deletion. Never expose service-role/SMTP/Google client secrets in Android bundles, environment variables intended for public use, repository evidence, or logs.
