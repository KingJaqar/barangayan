## 1. Intended outcome and change policy

Every audited editable input must automatically remain usable above the Android software keyboard when focused, including when focus moves while the keyboard is already open. Users must not have to dismiss the keyboard or manually reposition the screen before they can see what they are typing.

For a single-line input, the editable text area and caret must fit inside the unobscured viewport. For a multiline input taller than the available space, the active editing viewport and caret line must remain visible, with all content reachable through native input scrolling and/or the enclosing form's scrolling. Requiring the entire contents of an arbitrarily tall multiline field to be simultaneously visible is not a meaningful acceptance condition.

**Baseline evidence (Phase 0):** MuMuPlayer native checks covered 19 editable definitions: eight reproduced initial-focus bounds failures (C04–C06/C08–C11 in Profile; B32 in Delete Account), eleven limited visible observations and zero full-protocol passes. These are historical baseline counts; later Phase 1/2 candidate evidence is recorded in their progress sections. Unexecuted consumer/configuration cases remain pending under the current MuMuPlayer scope in section 9.0. The 49 B/C fields must not automatically become 49 fixes: retain handling that completes native acceptance. The 10 A fields also require verification because an explicit wrapper alone does not establish usable editing. [Native results](evidence/resident-android-keyboard-avoidance/phase-0-2026-10-24/mumu-2026-10-24/native-results.json).

Each field/route occurrence will end in one of these decisions:

| Decision | Evidence required | Implementation consequence |
|---|---|---|
| Retain existing handling | Native Android baseline passes focus, typing, scrolling and dismissal tests. | No application change. Keep the passing result in the validation ledger. |
| Repair layout/scrolling | The native mode is resize, but measured form/scroll bounds or a sibling footer still extend into the IME; alternatively, resizing occurs but content constraints prevent visibility. | Correct the smallest Android-specific layout constraint; keep native resize as the keyboard-height adjustment. |
| Add focus reveal | The usable viewport and scroll range are correct, but native focus reveal misses an input or a later content/layout change. | Add scoped, measured focus-to-scroll coordination to that scroll owner. Do not add keyboard-height padding. |
| Add/tune local avoidance | The specific screen or native Modal still overlaps the keyboard after its bounds are corrected, or an existing wrapper adds a duplicate displacement. | Configure the existing local wrapper or add one at that form's root. Select Android behavior from measured results; remove competing adjustment in that same surface. |
| Reopen for investigation | A field cannot be reached in its real conditional branch, or geometry/device evidence is incomplete. | Keep native acceptance unverified and do not label an unobserved field a confirmed bug. Phase 0 may close its explicit-gap checkpoint without closing native or overall acceptance. |

Maintain the current native resize mode. Do not switch the whole app to `adjustPan`, wrap the app navigator in a new avoidance container, or add a wrapper around every input. Successful work may produce many verified no-change entries and a small code diff.

## 4. Phase 1 — Establish only the shared mechanics required by baseline failures

**Dependencies:** Phase 0 decisions. **Skip application edits in this phase if existing owners can solve the failures directly.**

### 4.1 Resize and layout rules

- Confirm a bounded flex chain from screen/modal root to the scrollable body. A ScrollView requires a bounded viewport; do not replace that with an unbounded content container. [React Native ScrollView](https://reactnative.dev/docs/scrollview).
- Measure the usable region after resize. Fixed sibling headers/footers reduce the remaining body height; absolute overlays may obscure content without changing its measured scroll area. Account for each obstruction once, using actual layout bounds.
- Preserve safe-area padding. Do not add keyboard height to both the wrapper and the scroll body, or subtract keyboard height from a viewport already reduced by native resizing.
- Use `keyboardVerticalOffset` only for a demonstrated coordinate origin/header displacement. Derive it from the actual containing layout; do not set it to keyboard height or guess a universal header constant.
- Keep iOS `padding`, offsets, insets and dismissal behavior unchanged. Android-only adjustments must be explicitly platform scoped, including styles that would otherwise affect both platforms.

### 4.2 Optional measured focus reveal

Prefer the existing native focus reveal. If more than one proven failure needs the same additional coordination, introduce a small Android-only helper such as `src/hooks/use-android-focused-input-visibility.ts`; otherwise keep a narrow adaptation at the existing form owner. This is a proposed future file, not a mandatory abstraction.

Its contract must be:

1. Receive the actual active input/ref and its owning scroll container. Measure both in one window coordinate system after focus and the resulting viewport layout settles.
2. Derive the unobscured interval from the measured scroll viewport, known keyboard frame when available, and any overlapping footer. Use the minimum visible bottom boundary, rather than subtracting the IME height again from an already resized viewport. Keep a small design spacing margin, such as 8 dp, rather than a keyboard-sized spacer.
3. Scroll only the smallest required delta, within the valid content range, and only if the focused editing area is outside that interval. A focus action on an already visible input must not jump the form.
4. Recheck when focus moves with the keyboard open, viewport/body/footer size changes, a conditional section/error message appears, or multiline content size changes. Coalesce layout checks; do not update the whole screen on every selection or keystroke.
5. Let native TextInput manage caret scrolling within a bounded multiline viewport. If field growth exceeds the available space, apply an Android-only maximum editing height and native internal scrolling at the failing field/container, then verify start/middle/end selection. Do not attempt to infer caret pixel geometry from character indices.
6. Compose existing focus, blur, layout, content-size and selection callbacks rather than overwrite them. Reuse TextField's existing callback forwarding; add access to its native ref only if required, preserving its internal password-toggle ref.
7. Ignore detached or unmounted inputs, paused/closing Modals, unfocused routes and stale asynchronous measurements. Cancel queued frames and subscriptions on blur, route change and unmount. Recheck on the next real focus/open rather than retaining stale keyboard measurements.
8. Do not automatically reset all scroll positions on blur or keyboard hide. Remove only keyboard-specific accommodation and clamp out-of-range offsets after the layout expands; preserve meaningful user scroll and the existing step-navigation reset semantics.

Keyboard events may assist measurement, but they must not be the only trigger. Android uses `keyboardDidShow`/`keyboardDidHide`; delivery has documented limitations with some older Android/soft-input combinations. Handle current visibility/metrics when mounting with the keyboard open and use actual viewport layout changes as well. Validate against the installed SDK and supported Android floor. [React Native Keyboard API](https://reactnative.dev/docs/keyboard).

**Potential shared files:** the optional helper above; TextField only for needed ref/callback composition; existing sheet/StepFlowScreen owners only where their consumers reproduce a shared failure. No provider-wide wrapper or global behavior change.

**Exit criteria:** The selected mechanism fixes representative reproduced cases without moving an already visible field or adding a duplicate blank area. Passing baseline consumers remain passing, and the iOS paths remain unchanged.
